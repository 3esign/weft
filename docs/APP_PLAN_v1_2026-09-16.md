# WEFT Studio — plan for a general-purpose, run-anywhere WEFT application

Version 1 of the plan, 2026-09-16. Written as a build simulation against the repository as it stood on 2026-09-08
(the last state I could read file by file) plus what the STRAND manuscript, the specimen ledger and the Gate source
established this week. Where the simulation depends on something I could not re-check today because the laptop link
dropped mid-read, the item is marked **[verify]**. The questions at the end are the ones the simulation produced;
they are real decisions, not guesses.

---

## 0. What the app is for, in one paragraph

A person with a desktop 3D printer opens one program, describes or imports a form, and gets back either a woven
single-thread machine file that the Gate has passed, or a refusal that says exactly where the form leaves the
qualified domain. The person never runs Python, never opens a terminal, never edits JSON by hand. Two things stay
exactly as they are in the research code: the emitter (Level 3) and the Gate. Everything else — the modelling, the
import, the first-layer protection, the printer profiles, the interface — is built around them.

Non-goals for v1: a general slicer (WEFT prints single-wall lattices, nothing solid), multi-material, tree supports,
printing anything the Gate did not pass.

### 2.1 GeometryIR — the contract between modelling/import and the weave

Printer-neutral, explicit units (mm), no G-code, no machine parameters (this is the boundary the 2026-09-04 plan
already drew). One file per design, JSON, versioned:

- `bodies[]`: each body = a stack of closed planar contours per Z level (`z`, `points[]`, `role: wall|foundation|window-arc`),
  plus a `topology` list of events with Z: `birth`, `split(n→m)`, `merge(m→n)`, `death`, `hole-birth`, `hole-death`, `crown-open|crown-close`.
- `openings[]`: windows (start/end Z, angular span, lintel span in mm), courtyards (radius profile over Z).
- `bands[]`: height ranges with grammar (`staple|diagonal|perp|sine|eight`), node phase (`stacked|sine|helical`), density, tab count, wall depth.
- `declared[]`: everything the operator declares that the Gate will need — `maxbridge`, `maxcantilever`, `maxislands`, `experimental: true|false`.
- `provenance`: source (modeler primitives with parameters | import file sha256 + import settings), app version, date.

Rule inherited from the paper: L2 may *believe* anything about this file; only the Gate on the final G-code decides.

### 2.2 Modeler — WEFT-able forms only

Not a general CAD. A parametric shell modeller whose every output is a single-wall, contour-stackable form:

1. Primitives: cylinder, cone/frustum, dome (spherical cap with `capClose` off by default), rounded square / polygon
   tower, vase by revolve curve (Bezier profile, the current `vase` family), plate (the LIMIT16/MERA instrument plate as a
   first-class object for machine qualification).
2. Operations that stay contour-stackable: taper (radius over Z curve), twist (turns over height, as GORA 0.2 turns),
   "breathing wall" (wall depth over Z), loft between two profiles, array on a slab with planned merges (the Šuma
   family: n columns → merges at declared Z — the one topology the compiler has printed correctly), windows (open arcs
   with lintel spans), courtyard (interior hole with a declared minimum radius — the hole rule 7.75 mm from Šuma 2x2).
3. Constraints enforced at model time, not at export: minimum corner circle so the wall never overlaps itself; minimum
   hole radius `w/2 + e + rho`; contour spacing ≥ bead; no cap layers unless a qualified closure grammar is chosen.
4. Output: GeometryIR. The Modeler never touches nodes or threads.

### 2.3 Importer — meshes become skins

`GLB`, `GLTF`, `STL`, `OBJ`, `3MF (mesh only)`. Pipeline: load (three.js loaders) → unit and orientation dialog (scale to
mm, choose up axis, place on bed) → **plane slicing at the machine's layer height** (mesh–plane intersection → closed
polylines per Z) → contour cleaning (weld, simplify to the bead resolution, orient) → contour tree over Z (this *is*
Level 1: births/splits/merges/deaths become GeometryIR topology events) → **WEFT-ability report** before anything else:

- bodies whose contour changes faster than the qualified overhang per layer (the 0.8 mm/layer horns on GORA is the
  evidenced ceiling; steeper is refused or flagged);
- holes that shrink below the hole rule;
- bridges implied by merges longer than the declared `maxbridge`;
- a top that closes (the mesh has a lid) — offered as *open crown* or as the woven iris, never as a spiral cap;
- interior solids: an imported closed solid becomes its outer skin; inner shells are offered as separate bodies or dropped.

The report is the honest part of import: most meshes are not WEFT-able as they are, and the app says which layers fail
and why, in the Gate's own vocabulary, before the person spends a night printing.

### 2.4 Weaver — Level 1 + Level 2, ported to JavaScript

Port of the Python generators into `core/weft_weave.js` with the current strategies preserved as named "families"
(`suma`, `vase`, `plate`, `climber`, `sculpture`, `paired`, `aero_tower`). Acceptance is mechanical: for each of the 13
physical specimens and the built-only fixtures, the JS Level 2 must reproduce the archived geometry JSON that
`--geo` consumed (golden files, byte-equal after canonical float formatting). Only after that does the Weaver accept
GeometryIR from the Modeler/Importer. Node registration across merges and splits, band grammars, phase modes, tabs,
density grading over height and the woven-iris crown stay exactly the code that printed, moved, not rewritten.

### 2.5 Emitter and Gate — unchanged, in-process

`core/weft_core.js` and `core/weft_gate.js` are consumed as they are. The Gate runs inside the app on every export and
its verdict JSON is shown in the 3D preview: supported (green), legal bridge (amber), refused classes (red, with the
layer and coordinates), travel (grey hairs — the thing the Gate does not screen, drawn so the person sees it). An
export button does not exist until the Gate has passed; a declared experimental ceiling is shown as a banner on the
preview and written into the manifest, exactly as OBLAK/GORA were filed.

### 2.6 First-Layer Guard

The evidence says the first layer is where prints are lost cheaply: Šuma 4x4 v2 came out as eight separate pads with
no island limit set; every later build was gated to one island and every one of them stayed on the bed. The Guard is a
rule set applied between Weaver and Emitter, with machine-specific values from the profile:

1. `maxislands = 1` is the default for every export; a plate of loose feet is refused, not warned.
2. Foundation ribs: bodies that start apart on the first layer are joined by ribs (the "connected foundations the
   elements pull out of" rule from 2026-09-02), with openings between them so the foundation is one island with holes,
   not a slab.
3. Brim/skirt per machine: ring count and width from the profile (Studio auto-brim 5 mm is the A2L baseline); the brim
   is emitted as WEFT paths so it is inside the Gate's raster, not added by a slicer afterwards.
4. Bed zone: everything at or below `bedz` (0.5 mm default) is exempt from support checking and counted as support —
   the Guard makes this visible and lets the profile change it.
5. First-layer overrides from the profile: speed, temperature, fan off, Z offset, purge line placement (the purge
   stripe must not enter the raster as a 200 mm "floating" path — the Gate's start-block exemption already handles this
   when the header is labelled; the Guard guarantees the label).
6. A **first-layer preview** that shows the exact footprint and the islands count before export, on the machine's bed
   outline, with the purge line drawn.

### 2.7 Machine Profiles v2 and the slicer-export wizard

`machines.json` v2, one record per printer, with provenance on every number:

```
{ "id": "bambu-a1-lab-03", "family": "Bambu A1", "firmware": "bambu", "flavor": "marlin-like",
  "bed": {"x":256,"y":256,"z":256,"origin":"front-left"}, "nozzle": {"d":0.4, "source":"slicer-export"},
  "bead": {"w":0.45, "source":"assumed|coupon-C1|completed-prints", "evidence":"specimens/..."},
  "layer": {"h":0.24, "source":"slicer-export"},
  "start_gcode": {"text":"...", "source":"harvested from <file> sha256 ...", "roles":["startblock"]},
  "end_gcode": {...}, "temps": {"nozzle":220,"bed":65,"first_layer":{...}},
  "speeds": {"first_layer":..., "wall":...}, "retraction": {"length":..., "speed":..., "policy":"as-slicer"},
  "package": "gcode.3mf|gcode", "qualified": {"maxbridge":16, "maxcantilever":4.8, "evidence":"LIMIT16_A2L_v1"} }
```

The wizard: the person slices any small object in their own slicer (Bambu Studio, Orca, Cura, PrusaSlicer) and drops the
result on the app. The app reads the header comments and the start/end blocks (every slicer writes its settings into
the file), fills the profile, and marks every value with `source: slicer-export`. The bead stays `assumed` until the
person prints the **C1 bead coupon** (already a generator) and enters the caliper reading, or until two completed
prints exist at that bead (the A2L's own standard). The LIMIT16 plate becomes a built-in "qualify this printer" job that
fills `qualified.maxbridge` from what printed. This is how the four A1s in the lab get real profiles rather than the
current `A1 0.45 ASSUMED`.

Flavors for v1: Bambu (`.gcode.3mf` package, the existing packer), Klipper/Marlin plain G-code (Ender). Others when a
sliced file arrives — the wizard is written so that a new flavor is a header parser plus a package rule, nothing in the
Weaver or the Gate changes.

### 2.8 Shell, packaging, entry points

- **Electron** shell (Node in-process, so `core/*` runs unchanged; file dialogs; later, direct printer upload over
  Moonraker for Klipper and LAN mode for Bambu). Portable builds for Windows, macOS, Linux; no installer required.
- **PWA** of the same modules for the zero-install case (everything except direct printer upload runs in the browser
  already — the studio proved it).
- **CLI** stays: `weft build project.weft.json` must produce the same bytes as the app's export (parity test, as today).
- **MCP / usage contract**: one entry point with a written contract (`MCP_START_HERE.md` exists) so that a model can
  drive the app the same way a person does — propose parameters inside the contract, never write paths.

### 2.9 Ledger hook

Every export writes `specimens/<date>_<name>/`: the project file, the GeometryIR, the G-code or package, the Gate JSON,
the manifest (sha256 of every file, app version, machine profile snapshot, declared ceilings). The photograph and outcome
fields are filled by the person later, with the same form the ledger uses. This is the discipline that made the paper
verifiable; the app should produce it by default rather than reconstruct it afterwards.

## 3. Phases, deliverables, acceptance

Each phase ends with something runnable and a test that a fresh mind can execute without the writer's context.

**Phase 1 — Level 2 port and GeometryIR (2–3 weeks)**
`core/weft_weave.js` reproduces the Python generators on the golden files; GeometryIR schema in `schemas/`; the

filed in the ledger (the first app-built physical specimen).

**Phase 2 — Import and WEFT-ability (2 weeks)**
GLB/STL/OBJ loading, slicing to contours, contour tree, report. Done when: the Eiffel-tower showcase (28 cm) goes from a
mesh to a Gate-passed file with a report that names every refused layer; one imported form is printed.

**Phase 3 — First-Layer Guard and machine wizard (2 weeks)**
Guard rules, first-layer preview, `machines.json` v2, wizard from slicer exports (Bambu Studio and one of Orca/Cura/
Prusa), C1 coupon and LIMIT16 job as built-in "qualify" flows. Done when: an A1 from the lab has a profile whose bead
source is `coupon-C1`, and a build exported from the app prints on it with the foundation as one island.

**Phase 4 — Shell and release (2 weeks)**
Electron portable builds + PWA; English documentation with the rails applied (no local paths, no "measured" where the
record says assumed); sample projects (the printed specimens as examples); MCP contract updated. Done when: a colleague
who has never seen the repository opens the app on their own laptop, imports their slicer file, builds a vase, and gets a
gated export — timed, recorded, and filed as the first external-user test.

**Phase 5 — After v1**
Direct printer upload; band grammar mixing and height-graded density as Modeler operations; a qualified crown-closure
grammar (the woven iris, measured); thermal/accelerometer telemetry back into the Gate (the paper's future work);
concrete/clay profiles (GeometryIR is already unit-explicit and bead-agnostic — the profile decides).

## 4. The walk-through (what the person does, module by module)

1. Open WEFT Studio. First run: "Add a printer" → drop `benchy.gcode.3mf` from Bambu Studio → profile created, bead marked
   assumed, banner: "print the C1 coupon to measure the bead".
2. New design → Tower → height 190, base 134, top 28, twist 0.2, wall 3.2→1.8, windows: 4 at Z 60–120 with 30/40/50 mm
   lintels. The Modeler refuses the 50 mm lintel because the profile's qualified bridge is 16 mm; the person either
   lowers it or ticks "experimental ceiling 60 mm" (banner appears, manifest will carry it).
3. Weave: bands — staple below 60, sine 60–120, staple above; helical phase; density graded 1.0→0.7 over height; crown:
   open (default) or woven iris.
4. Build → Gate runs (a few seconds for ~700 k points in JS) → preview shows two red runs at the window tops → the person
   raises the lintel Z by two layers → Gate passes → first-layer preview: one island, brim 5 mm, purge line outside the
   raster.
5. Export → `specimens/2026-10-02_tower_x1/` with package, GeometryIR, gate JSON, manifest. The file goes to the printer.
6. After the print: the person opens the specimen folder from the app, adds photos and the outcome line. The ledger
   grows the way the paper needed it to.

Every step in this walk-through maps to a module in §2; nothing in it requires a new algorithm except the mesh slicer
and the contour tree (standard computational geometry) and the Level-2 port (translation, guarded by golden files).

## 6. Decisions only you can make (the questions the simulation produced)

1. **Shell**: Electron portable builds + PWA (my recommendation: Node in-process, zero rewrite of `core/*`, printer
   upload possible later) — or PWA only (smallest, no printer upload, no file-system ledger hook)?
2. **Modelling scope**: parametric WEFT-able shells (primitives, loft, twist, windows, arrays with merges) plus import
   for freeform — or do you also want freeform mesh editing inside the app? (The latter is a different product; I would
   not build it.)
3. **Import semantics**: an imported closed solid becomes its outer skin as a single-wall lattice. Is that the intended
   reading of "import GLB" — the Eiffel tower as a woven silhouette skin — or do you want interiors handled somehow?
4. **Printers first**: the four Bambu A1s (all `assumed` today) — do we schedule C1 coupons and one LIMIT16 plate per
   A1 in Phase 3, so their profiles are measured rather than assumed? The Ender stays assumed until C1 prints there too.
5. **Slicer files**: which slicer exports will you send first (Bambu Studio `.gcode.3mf`, Orca, Cura, PrusaSlicer)? Each
   is one header parser; the first two cover the lab.
6. **Publishing**: public GitHub (`3esign/weft`) with English docs from Phase 4, or private until the STRAND review is
   through? Licence?
7. **Team**: which colleagues take the interface, the documentation and the A1 test prints? The Weaver port, the Gate
   integration and the Guard rules stay with the compiler mind (yours + mine); the rest is delegable with the rails.
8. **The backlog since 09-05** (untracked geometry files, specimen READMEs, tests): commit as-is, or review first?

Answer these and Phase 0 starts on the repository as it is; nothing here needs a decision that is not on this list.
